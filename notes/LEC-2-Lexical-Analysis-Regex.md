## 1. 本讲要抓住什么（p.2、11、39）

**词法分析器（Lexer）按照语言的词法规约，把字符流转换为带源码位置的 Token 流，交给语法分析器（Parser）。**

```text
源程序字符流
    ↓ Lexer：切分、分类、记录位置
Token Stream
    ↓ Parser：组合语法结构（后续课程）
AST
```

本讲需要理解的几个问题：

- 为什么不能用通用 `split()` 给程序分词？
- 如何用正则表达式定义一类 Token 可以匹配的文本？
- 多条规则同时适用时，怎样决定匹配长度和 Token 类别？
- 如何处理空白、错误以及字符串等不同词法上下文？

**完整词法规约不仅包含正则模式，还包含动作、规则优先级，以及需要时使用的 mode。**

## 2. Lexer 的输入与输出（p.3–10）

### 2.1 字符本身没有标出 Token 边界

对于下面的程序：

```c
int y = x + 1;
```

人会自动识别关键字、名字、运算符和整数，但编译器最初看到的只是字节或字符序列。Lexer 必须同时完成：

1. **切分（partition）：** 当前词法单元从哪里开始、在哪里结束？
2. **分类（classification）：** 这段文本属于哪一种 Token？

课件中的输出为：

| Lexeme（匹配文本） | Token | 起始偏移（从 0 开始） |
| --- | --- | --- |
| `int` | `KW_INT` | 0 |
| `y` | `IDENT("y")` | 4 |
| `=` | `ASSIGN` | 6 |
| `x` | `IDENT("x")` | 8 |
| `+` | `PLUS` | 10 |
| `1` | `INT_LITERAL(1)` | 12 |
| `;` | `SEMICOLON` | 13 |

空白通常不作为语法 Token 交给 Parser，但 Lexer 必须先识别空白，才能正确跳过。

### 2.2 Token kind、lexeme 与 value

| 概念 | 含义 | 例子 |
| --- | --- | --- |
| Token kind | 词法单元的类别 | `IDENT`、`INT`、`PLUS` |
| Lexeme | 本次实际匹配到的源码文本 | `adjust`、`42`、`+` |
| Value | 根据文本生成的语义数据 | 整数值 `42`，或标识符的名字 |
| Token | 扫描得到的一条记录 | 类别、文本／值及源码位置的组合 |

`adjust` 与 `x` 的 lexeme 不同，但 kind 都可以是 `IDENT`。从模式的角度看，`IDENT` 对应所有合法标识符组成的集合，某个 lexeme 是其中一个元素。

**补充理解：** Lexeme 与 value 不一定相同。例如，整数字面量的源码文本可以是 `"0042"`，转换后的值是整数 `42`；字符串的 lexeme 包含源码中的引号，处理后的 value 可以只保留字符串内容。具体转换由语言规则和 action 决定。

### 2.3 Token 还必须携带 source span

课件给出的 Token 信息包括：

| 字段 | 用途 |
| --- | --- |
| `kind` | Parser 据此选择语法规则 |
| `lexeme / value` | 名字解析、常量处理与 AST 构造 |
| `source span` | 定位源码、生成错误诊断 |
| `trivia`（可选） | 为格式化器、IDE 等保留空白和注释 |

例如：

```c
int y = x + ;
```

Parser 能发现 `PLUS` 后面缺少表达式，但只有保留了 Token 的 span，才能指出错误在源文件中的位置。AST 节点的位置也通常根据 Token 的位置组合得到。

课件用 `1-based line:column` 展示位置，实现中也常保存 `0-based byte offset`。

**补充理解：** 课件 p.35 的区间可以按左闭右开理解，例如第一行的 `int` 占据 `[1:1, 1:4)`，`adjust` 占据 `[1:5, 1:11)`。实现时应明确区间端点和列号的计数约定；包含非 ASCII 字符时，字节偏移与字符计数可能不同。

### 2.4 Lexer 与 Parser 的接口契约

```text
nextToken() -> Token

Token {
    kind,
    value / lexeme,
    span
}
```

Parser 主要根据 `kind` 判断语法结构；构造 AST 或报告错误时，再使用 `value` 与 `span`。这种稳定的输入输出接口，让词法分析和语法分析可以分别实现与验证。

## 3. 为什么不能直接 split（p.12–16）

按空白切分下面的代码，看起来似乎可行：

```c
int y = x + 1 ;
```

但下面的字符串立即构成反例：

```c
print("a b");
```

按空白切分会得到 `print("a` 和 `b");`，正确结果却应是：

```text
IDENT("print")  LPAREN  STRING("a b")  RPAREN  SEMICOLON
```

这里 `STRING("a b")` 中的参数表示字符串的值，源码 lexeme 则包含两侧双引号。

这个例子说明：

- **有空白未必是边界：** 字符串内部的空格属于字符串内容。
- **没有空白也可能存在边界：** `print`、`(`、字符串、`)`、`;` 仍然要分开。

因此，Lexer 从**当前位置尝试匹配 Token 模式**，用模式决定边界和类别，再从消费后的新位置继续扫描。空白本身也可以是一条模式，匹配成功后的动作是跳过。

## 4. 用形式语言描述 Token 模式（p.17–18）

自然语言可以描述“标识符以字母或下划线开头”，但实现需要精确定义。课件把每种模式表示成一个字符串集合：

```text
L(IDENT) = { "x", "y", "print", "value2", "_tmp", ... }
L(INT)   = { "0", "1", "2", "10", "42", ... }
L(LE)    = { "<=" }
```

判断某段文本是否符合模式，就是判断它是否属于对应的集合。

| 术语 | 含义 |
| --- | --- |
| 字母表 Σ（alphabet） | 允许使用的字符集合 |
| 字符串（string） | 字母表中字符组成的有限序列 |
| 语言 L（language） | 由字符串组成的集合 |
| 正则语言（regular language） | 能由正则表达式描述的语言 |

**补充理解：** `Σ*` 表示 Σ 上所有有限字符串的集合，包含空串 `ε`；形式语言满足 `L ⊆ Σ*`。空串 `ε` 是长度为 0 的字符串，`{ε}` 是只包含空串的语言，`∅` 则是不含任何字符串的空语言。

词法分析通常选择正则语言来描述 Token 模式。**正则表达式描述的是一组可能的 lexeme，而不只是某一个具体文本。**

## 5. 正则表达式的基本构造（p.19–20）

### 5.1 核心操作

下面的 `A`、`B` 表示正则表达式，`L(A)` 表示 A 描述的语言。

| 构造 | 记号 | 含义 |
| --- | --- | --- |
| 单字符 | `'c'` | 只匹配字符 `c`，语言为 `{ "c" }` |
| 空串 | `ε` | 匹配长度为 0 的字符串，语言为 `{ "" }` |
| 连接 | `AB` | 先匹配 A，再匹配 B |
| 选择 | `A \| B` | 匹配 A 或 B，语言为 `L(A) ∪ L(B)` |
| Kleene 星号 | `A*` | 将 A 重复零次或多次 |

连接的集合定义是：

```text
L(AB) = { xy | x ∈ L(A), y ∈ L(B) }
```

例如：

```text
ab       匹配 "ab"
a|b      匹配 "a" 或 "b"
ab*      匹配 "a"、"ab"、"abb"、...
(ab)*    匹配 ""、"ab"、"abab"、...
```

**补充理解：** 常用优先级是“重复高于连接，连接高于选择”。所以 `ab|c` 表示 `(ab)|c`；`ab*` 表示 `a(b*)`。有歧义时用括号明确分组。

### 5.2 常用简写

| 写法 | 等价形式或含义 |
| --- | --- |
| `A+` | `AA*`，一次或多次 |
| `A?` | `A \| ε`，零次或一次 |
| `[0-9]` | 十个数字字符的选择 |
| `[A-Za-z_]` | 大写字母、小写字母或下划线 |
| `[^"\n]` | 匹配一个既不是双引号、也不是换行的字符 |
| `(AB)` | 把 AB 作为整体分组 |

这些写法提高可读性，不增加这里所讨论的正则表达能力。

**补充理解：** `[^"\n]` 中的 `^` 对字符集合取反，具体范围由字母表决定。课件使用的固定字符串记法如 `'int'`、`'+'`，表示匹配字面文本；落到具体正则工具时，要遵守该工具的引用和转义语法。

## 6. 常见 Token 的正则模式（p.21–22）

### 6.1 非负整数

```text
digit   = [0-9]
integer = digit+
```

- 完整匹配：`0`、`7`、`42`、`2026`。
- 不能完整匹配：空串、`-42`、`3.14`。

**补充理解：** 这里讨论的是整个字符串是否属于 `L(integer)`。扫描 `3.14` 时，`integer` 仍能匹配前缀 `3`，后面的字符如何处理由其他规则决定。负号也常作为单独的 `MINUS` Token，负数表达式由 Parser 组合；这取决于语言设计。

### 6.2 标识符

```text
start      = [A-Za-z_]
rest       = [A-Za-z0-9_]
identifier = start rest*
```

合并后为：

```regex
[A-Za-z_][A-Za-z0-9_]*
```

- 完整匹配：`x`、`value2`、`_tmp`。
- 不能完整匹配：`2value`，因为首字符不能是数字。

**补充理解：** 在只有上述整数与标识符规则时，扫描器可能把 `2value` 切成 `INT(2)` 和 `IDENT("value")`。若语言要求将这种相邻写法报告为非法数字，就需要额外的规则或检查，不能仅凭“它不是标识符”推断 Lexer 一定报错。

### 6.3 简化字符串

课件先用一个受限的字符集合演示：

```text
quote       = U+0022       // 双引号字符
contentChar = [A-Za-z0-9 ] // 最后一项是空格
STRING      = quote contentChar* quote
```

这个模式允许空字符串 `""` 和 `"a b"`。字符串内部的空格由 STRING 模式一起消费，不会单独交给 WHITESPACE 规则。

**注意范围：** 这是教学用简化模式，尚未处理转义引号、反斜杠、任意标点或多行字符串。后面介绍 mode 时，课件讨论的是可以按上下文扩展的字符串规则。

## 7. 从正则模式到完整词法规约（p.23–26）

### 7.1 每条规则都包含模式与动作

课件的部分规则如下，排列顺序也是规约的一部分：

| 规则名 | 匹配模式 | 动作 |
| --- | --- | --- |
| `WHITESPACE` | `[ \t\r\n]+` | `skip` |
| `KW_INT` | `'int'` | `emit KW_INT` |
| `IDENT` | `[A-Za-z_][A-Za-z0-9_]*` | `emit IDENT(text)` |
| `INT` | `[0-9]+` | `emit INT(value)` |
| `PLUS` | `'+'` | `emit PLUS` |

**Pattern 决定允许匹配哪些文本，Action 决定匹配成功后产生什么数据或改变什么状态。**

例如，IDENT 的模式只负责识别名字；`emit IDENT(text, span)` 才负责把文本和位置组织成 Token。INT 的动作还可以把数字文本转换成整数值。

### 7.2 三类常见动作

| 动作 | 行为 | 典型用途 |
| --- | --- | --- |
| `emit` | 消费输入并产生 Token | 标识符、整数、运算符 |
| `skip` | 消费输入，不向 Parser 返回 Token | 空白、普通注释 |
| `control` | 执行诊断或改变词法状态等控制逻辑 | 非法字符、字符串处理、注释处理 |

**补充理解：** 即使一条规则使用 `skip`，也必须更新位置。实现 `nextToken()` 时通常会继续扫描，直到遇到需要返回的 Token 或输入结束。

## 8. 两层选择：最长匹配与规则优先级（p.27–32）

仅有“符合某条模式”还不能唯一决定结果，因为存在两类冲突。

### 8.1 长度冲突：Maximal Munch

扫描 `foo+3` 时，`f`、`fo`、`foo` 都符合 IDENT 模式。如果第一次成功就返回，会把一个名字错误地切成多个名字。

**最长匹配（maximal munch）选择从当前位置开始、能被某条规则接受的最长前缀。**

```text
候选文本    是否被 IDENT 接受
f           是
fo          是
foo         是 ← 最后一次成功
foo+        否，且不能继续成为 IDENT
```

所以先产生 `IDENT("foo")`，下一轮从 `+` 开始。

### 8.2 类别冲突：同长时按规则顺序

假设规则顺序为：

```text
KW_IF : 'if'
IDENT : [A-Za-z_][A-Za-z0-9_]*
```

对于输入 `if`，两条规则都匹配长度 2。课件采用常见约定：**同长时选择排在前面的规则**，因此返回 `KW_IF`。

对于 `ifx`，IDENT 能匹配长度 3，而 KW_IF 只能匹配长度 2，所以返回 `IDENT("ifx")`。

**决策顺序必须是：先比较长度，再比较规则顺序。规则优先级不能推翻更长的匹配。**

### 8.3 共享前缀的运算符

如果语言定义了以下运算符：

| 文本 | Token kind |
| --- | --- |
| `<` | `LESS` |
| `<=` | `LESS_EQUAL` |
| `<<` | `SHIFT_LEFT` |
| `<<=` | `SHIFT_LEFT_ASSIGN` |

扫描 `a <<= 1` 时，`<`、`<<`、`<<=` 都曾匹配成功，最终选择最长的 `<<=`。

### 8.4 “尚未成功”与“无法继续”的区别

**补充理解：** 课件所说的“读到所有规则都无法匹配”，应理解为当前前缀已经无法继续扩展成任何合法匹配，而不是“当前前缀还不是完整 Token”。

例如，读取字符串 `"a b"` 时，只读到开头的 `"a` 还不能形成完整 STRING，但后续可能遇到闭合引号，因此应继续。扫描器需要区分：

- **接受状态：** 当前读到的文本已经是合法 lexeme。
- **可继续状态：** 目前还存在通过后续字符完成匹配的可能。
- **无法继续：** 继续扩展当前前缀也无法匹配，应回到最后成功的位置。

如果回退，超前读取的字符必须留给后续扫描，不能丢失。下一讲的自动机和 `lastAccept` 会把这个过程落实为算法。

## 9. 执行词法规约（p.33–36）

### 9.1 课件给出的直接流程

```text
candidates = matchAll(rules, position)
if candidates is empty:
    diagnose(); advanceOneCharacter()
else:
    lexeme = chooseLongest(candidates)
    rule    = chooseFirstRule(candidates, lexeme)
    runAction(rule, lexeme, span)
```

理解这段伪代码时要注意：

1. `matchAll` 从**当前位置**尝试每条规则，不是在后面的任意位置搜索。
2. 每条规则最多返回一个候选，即它能匹配的最长前缀。
3. `chooseLongest` 在所有规则的候选中选最长文本。
4. `chooseFirstRule` 只在同长候选中按规则顺序选择。
5. 动作消费文本，更新位置，并决定是否返回 Token。

**补充理解：** 普通正则库的“第一个匹配”未必等价于这里的“最长前缀”。例如某些引擎对 `a|ab` 采用分支顺序优先，会在输入 `ab` 上先返回 `a`。实现 `matchAll` 时必须保证它满足课件规定的最长前缀语义。

### 9.2 完整扫描示例

课件使用：

```c
int adjust(int x) {
    int y = x + 1;
    return y;
}
```

开头几轮决策为：

| 本轮匹配文本 | 候选规则 | 决策 |
| --- | --- | --- |
| `int` | `KW_INT`、`IDENT` | 同长时选 `KW_INT` |
| 空格 | `WHITESPACE` | 消费并跳过 |
| `adjust` | `IDENT` | 返回标识符 |
| `(` | `LPAREN` | 返回左括号 |
| `int` | `KW_INT`、`IDENT` | 返回 `KW_INT` |
| 空格 | `WHITESPACE` | 消费并跳过 |
| `x` | `IDENT` | 返回标识符 |

只要规则覆盖其余符号与关键字，就能用同一流程继续扫描整段程序。

第二行的 Token 位置可表示为以下左闭右开区间：

```text
KW_INT       [2:5,  2:8)
IDENT(y)     [2:9,  2:10)
ASSIGN       [2:11, 2:12)
IDENT(x)     [2:13, 2:14)
PLUS         [2:15, 2:16)
INT(1)       [2:17, 2:18)
SEMICOLON    [2:18, 2:19)
```

### 9.3 跳过也必须发生在识别之后

不能在词法分析前盲目删除所有空白或注释，因为它们在字符串中可能只是普通内容。正确流程是先确定当前匹配的规则，再执行 `skip` 或保留为 trivia。

相同模式也可以绑定不同动作：编译器跳过注释，格式化器则保留注释和空白。

## 10. 错误恢复：报告位置并保证前进（p.37）

例如：

```c
int y = x @ 1;
```

假设 `@` 不匹配任何正常规则，Lexer 至少应：

1. 报告非法字符及其 span。
2. 消费至少一个字符，让扫描位置前进。

之后可以继续识别 `1` 和 `;`。是否额外返回 `ERROR_CHAR`，由 Lexer 与 Parser 的接口约定决定。

**补充理解：** 如果只报告错误而不移动扫描位置，下一轮会再次遇到同一个字符，形成死循环。同样，常规扫描规则通常应避免接受空串，否则成功匹配也可能不消费任何输入。EOF 应单独处理；本讲未规定具体 EOF Token 接口。

这里的恢复策略针对非法字符。未闭合字符串等跨字符错误还需要相应的诊断与恢复设计，本讲没有给出完整方案。

## 11. Lexer mode：按上下文选择规则组（p.38）

对于 `print("a b");`，普通代码中的空格可以跳过，字符串内部的空格则要保留。课件用 mode 表达当前的词法上下文：

| 当前 mode | 读到的内容 | 动作 |
| --- | --- | --- |
| `NORMAL` | 标识符 | `emit IDENT` |
| `NORMAL` | 空白 | `skip` |
| `NORMAL` | 开始双引号 | 进入 `STRING` mode |
| `STRING` | 允许的内容字符 | 追加到字符串内容 |
| `STRING` | 结束双引号 | 产生 STRING Token，回到 `NORMAL` |

在课件这个设计中，`/*` 只有在 `NORMAL` mode 才能开始注释；在 `STRING` mode 中，它是字符串内容。

**mode 先决定启用哪些规则，最长匹配与规则优先级再在这组规则内部工作。**

**补充理解：** 简单字符串可以用一条完整正则直接识别，也可以分 mode 逐步处理。mode 便于组织规则，但不会自动解决所有嵌套问题。例如任意深度的嵌套注释需要额外的深度计数或栈，仅靠有限个 mode 和普通正则不足以记录任意嵌套层数。

## 12. 下一讲的衔接（p.40）

本讲先把 Lexer 的行为规定清楚，下一讲讨论如何高效、机械地实现这些规则：

```text
Regex
    ↓ Thompson 构造
NFA（非确定有限自动机）
    ↓ 子集构造
DFA（确定有限自动机）
    ↓ 最小化、字符类、转移表与 lastAccept 等实现设计
nextToken()
```

逐条尝试规则会重复读取相同前缀；把规则合成自动机，可以共享扫描过程。`lastAccept` 用于记录最后成功的位置及对应规则，以实现最长匹配。

课件也提出：即使 LLM 能生成 Lexer，正式规约和确定性生成器仍是值得理解的环节。**补充理解：** 语言设计可以通过开放式探索形成，但最终需要明确的规则，才能检查实现是否稳定地遵守相同的 Token 边界、优先级与错误行为。

## 13. 复习自测

1. **Token kind 与 lexeme 有什么区别？**  
   kind 是类别，lexeme 是本次匹配到的实际源码文本。`foo` 和 `bar` 可以有相同 kind，却有不同 lexeme。

2. **为什么不能先按空白切开，再判断类别？**  
   空白可能属于字符串内部；相邻 Token 也可能没有空白。边界必须由词法模式确定。

3. **`A*`、`A+`、`A?` 分别表示什么？**  
   分别是零次或多次、一次或多次、零次或一次。若 A 本身不接受空串，`A+` 至少消费一次非空匹配；若 A 接受空串，`A+` 也可能接受空串。

4. **`ab*` 与 `(ab)*` 有什么区别？**  
   前者是一个 `a` 后跟零个或多个 `b`；后者是整段 `ab` 重复零次或多次，因此后者可以匹配空串。

5. **为什么 `if` 可以是关键字，而 `ifx` 是标识符？**  
   `if` 的关键字和标识符匹配同长，由关键字规则的优先级决定；`ifx` 的标识符匹配更长，长度优先。

6. **为什么读到 `<` 不能立即返回 LESS？**  
   后续字符可能组成更长的 `<=`、`<<` 或 `<<=`。应继续扫描并记录最后成功的匹配。

7. **当前前缀不构成完整 Token，是否就应停止？**  
   不一定。它可能仍能扩展为合法 Token，例如尚未读到结束引号的字符串。只有无法继续匹配时，才回到最后成功的位置；从未成功则进入错误处理。

8. **`skip` 是否意味着不用更新源码位置？**  
   不是。被跳过的字符仍然属于输入，必须消费并更新偏移与行列号。

9. **没有规则匹配时，为什么必须保证前进？**  
   否则会反复在同一位置报错，无法继续扫描。通常报告位置并至少消费一个字符。

10. **mode、最长匹配和规则优先级以什么顺序生效？**  
    mode 选择当前规则组；在其中选择最长匹配；同长时按规则顺序决定。

11. **本讲是否已经解决完整的语法结构识别？**  
    没有。本讲输出带位置的 Token 流，表达式、语句等结构由后续 Parser 处理。

## 1. 本讲要抓住什么

**编译器把源程序转换成目标程序，并保持源程序的语义。** 为了完成这项任务，编译器会不断改变程序的表示，让当前阶段需要处理的关系变得明确。

本讲的三个核心问题：

1. **编译器做什么？** 理解源程序、检查语言规则，并生成保持语义的目标程序。
2. **为什么编译过程要分阶段、换表示？** 不同表示突出不同信息，使对应的分析和变换更容易实现。
3. **AI 辅助编程时代，为什么还要学编译原理？** 要能提出正确的问题、明确语言与编译器的设计目标，并理解和判断生成的实现。

## 2. 编译器的基本任务（p.15）

课件用一个 C 函数展示源程序到目标程序的转换：

```c
int add1(int x) {
    return x + 1;
}
```

对应的简化 x86-64 汇编：

```asm
add1:
    mov  eax, edi
    add  eax, 1
    ret
```

这里最重要的是转换前后的**语义保持（semantics preservation）**：目标程序应实现源程序规定的行为。源程序不合法时，编译器还应给出诊断。

**补充理解：** 在这段示例采用的调用约定下，`edi` 承载整数参数，`eax` 承载整数返回值。汇编先复制参数，再加一，最后返回。具体寄存器与调用约定有关，不应把这个例子当成所有平台的统一规则。

“编译成功”和“程序符合作者意图”也有区别。编译器能检查语言规定的约束，但一个类型正确的程序仍可能写错算法。

## 3. 编译过程为什么需要多种表示（p.16–17）

课件给出的表示变化可以整理为：

```text
源程序字符及源码位置
    ↓ 词法分析
Token
    ↓ 语法分析
Parse Tree / AST
    ↓ 名字解析、类型检查
Bound AST / Typed AST
    ↓ 转换为中间表示
IR
    ↓ 程序分析与优化
目标程序（如 x86-64、RISC-V）
```

这是一张概念地图；具体实现可以合并某些步骤，也不必为每一种表示单独建立完整的数据结构。

### 3.1 不同表示分别让什么变得明确

| 表示 | 中文含义 | 显式表达的关系 | 适合做什么 |
| --- | --- | --- | --- |
| AST（Abstract Syntax Tree） | 抽象语法树 | 语言构造及其嵌套关系 | 递归遍历、名字解析、类型检查 |
| CFG（Control-Flow Graph） | 控制流图 | 基本块及其控制流边 | 判断可达路径、分析跨路径性质 |
| SSA（Static Single Assignment） | 静态单赋值形式 | 定义与使用之间的数据依赖 | 常量传播、删除无用计算 |
| Machine IR | 机器级中间表示 | 目标指令、操作数与资源需求 | 指令选择、活跃分析、寄存器分配 |

**核心思想：选择表示，就是选择哪些事实可以直接被看见和自动处理。**

### 3.2 几组容易混淆的概念

以下为补充理解：

- **Token 与 AST：** Token 是词法单元，例如标识符、整数常量和运算符；AST 组织这些单元所构成的语言结构，例如“函数体中包含一条返回语句”。
- **Parse Tree 与 AST：** 语法分析树更直接地反映文法推导结构；AST 通常省去括号等语法细节，保留后续处理需要的结构。
- **Bound AST 与 Typed AST：** 前者明确标识符对应哪个声明，后者记录或关联表达式等节点的类型信息。实现中可以在同一棵树上逐步补充这些信息。
- **IR、CFG 与 SSA：** IR 是中间表示的统称；CFG 表达控制流结构，SSA 组织值的定义与使用。一个 IR 可以同时具有 CFG 结构并采用 SSA 形式，它们不必是互相替代的三个阶段。

## 4. 编译器的阶段与运行时支持（p.18–21）

| 部分 | 核心问题 | 主要工作 | 主要表示或状态 |
| --- | --- | --- | --- |
| 前端（Front End） | 程序写了什么？是否有意义？ | 词法、语法、名字解析、类型检查 | Token、AST、Typed AST |
| 中端（Middle End） | 怎样表示、分析和改变程序？ | IR、SSA、程序分析、优化 | SSA 风格 IR |
| 后端（Back End） | 怎样在目标机器上执行？ | 指令选择、活跃分析、寄存器分配 | Machine IR、机器指令 |
| 运行时支持（Runtime Support） | 哪些工作必须动态完成？ | 对象布局、内存分配、垃圾回收等协作 | 运行时状态 |

### 4.1 前端：识别结构，建立含义

前端包含两类任务。

**识别程序结构：** 从源程序字符得到 Token、AST。相关内容包括词法规则、有限自动机、上下文无关文法、LL / LR 分析与错误恢复。

**建立程序含义：** 从 AST 得到名字绑定和类型信息。相关内容包括作用域、名字绑定、类型规则、类型推导与错误诊断。

可以用两个问题区分它们：

- “这段代码是不是一个合法的函数调用结构？”属于语法层面。
- “调用的函数是谁？参数类型是否符合要求？”属于语义分析层面。

前端训练的是：**把语言规格变成识别算法，把语言规则变成可检查的判断。**

### 4.2 中端：在表示上推理，再变换程序

中端首先要把执行过程所需的信息显式化，包括求值顺序、临时值、基本块、控制流、类型和内存信息。

然后通过程序分析，从局部指令推导跨路径成立的事实。课程会涉及：

- **Def-use 关系：** 一个值在哪里定义，在哪里使用。
- **数据流分析与不动点：** 沿程序结构传播信息，直到分析结果稳定。
- **常量传播：** 利用已知的常量事实简化计算。
- **死代码删除：** 删除不影响程序可观察行为的无用计算。

**补充示例：** 假设下面采用普通整数运算，且这些局部计算没有额外副作用：

```text
a = 2
b = a + 3
return b
```

分析知道 `a` 恒为 `2`，就能推出 `b` 恒为 `5`，进而将其简化为：

```text
return 5
```

这里的关键是先有分析依据，再实施变换。对于带副作用的调用或可能触发异常的操作，不能仅凭“结果没有被使用”就删除。

中端训练的是：**选择适合问题的表示，并在保持语义的前提下变换程序。**

### 4.3 后端：在机器资源约束下实现语义

后端需要解决抽象程序与真实机器之间的差异：

- **指令选择：** 用目标机器的哪些指令实现一个抽象操作？
- **活跃分析：** 一个值在某个程序位置之后是否还可能被使用？
- **寄存器分配：** 如何让大量临时值使用有限的物理寄存器？
- **Spill：** 寄存器不足时，将部分值放入内存，并在需要时读写。

后端训练的是：**在目标指令集和有限机器资源的约束下实现语言语义。**

### 4.4 运行时：处理执行时才能确定的信息

课程还会讨论调用边界、对象布局、内存分配和垃圾回收（GC）。例如，对象什么时候不再需要，往往取决于程序实际执行时的状态。

**补充理解：** 运行时支持贯穿编译器设计与程序执行，不是生成机器代码之后再做的一次编译变换。编译器可以决定对象布局、生成运行时调用或提供元数据，运行时利用这些约定完成动态工作。

这里要学会划分：**哪些信息可以静态处理，哪些行为需要动态支持，以及两者如何协作。**

## 5. 课程的另一条主线：用编程语言理解系统（p.23）

编程语言可以把系统中的隐含假设变成**可检查、可利用的信息**。语言设计提供的约束，还能成为系统设计和优化的依据。

| 课件中的问题 | 语言视角 | 希望获得的能力 |
| --- | --- | --- |
| 如何让 shell 的字符串输出更可控、可检查？ | 类型系统、类型论 | 将输出表达为有字段、有类型的数据，例如按 CPU 字段筛选进程 |
| 如何利用读写约束优化分布式共享内存？ | 所有权（Ownership） | 利用“一个写者、多个读者”等约束辅助系统设计 |
| 如何更轻量地保存、切换和恢复执行状态？ | 控制流、协程 | 理解寄存器、栈及权限／保护等上下文状态的组织方式 |

这些是课程指出的后续探索方向，本讲尚未展开具体实现。

## 6. AI 时代的学习方法（p.5–13）

### 6.1 教学重点为什么调整

课件回顾了课程从以前端为主、到完整 Tiger 编译器、再到引入 LLVM 的演变。过去的教学尤其重视实现能力，以及中大型 C/C++ 项目的阅读和开发经验。

面对随时可用的问答模型与编程助手，教师提出两个更重要的目标：

- 能够**提出正确的问题**。
- 清楚**自己要实现什么**。

### 6.2 “解构力”与“建构力”

| 能力 | 在本课程中的理解 |
| --- | --- |
| 解构力 | 理解已有内容的结构、假设、推理和设计选择，包括模型生成的内容 |
| 建构力 | 根据自己的目标组织知识、制定规则，并形成可解释的设计与实现 |

课件提出的问题是：**如何把模型输出转变为自己的东西？** 这里的“东西”既包括单点知识，也包括对大规模问题的认知和思考方法。

课程因此强调更强的逻辑、更高的知识密度、更多“为什么”，以及可以借助模型继续深入的方向。

**学习建议（根据课件整理）：** 对模型生成的一段实现，尝试回答“它实现了哪条语言规则”“依赖哪些假设”“什么测试能暴露错误”“如果规则改变，哪些地方需要调整”。能回答这些问题，才能判断实现是否符合自己的设计。

## 7. 新版 Lab：设计自己的语言与编译器（p.24–30）

### 7.1 旧版与新版的区别

旧版 Lab 围绕 Tiger 编译器，逐步完成 Lexer、Parser、Type Checking，再将 Typed AST 转换为 LLVM IR。它能锻炼完整编译流程与中大型项目开发能力，但手工实现门槛高，设计空间也较固定。

新版 Lab 允许在规定的可选语言风格内设计具体语法。课件列举了 Tiger、Python、C/C++、Rust 等风格；这并不意味着必须完整实现这些现有语言。

**新版约束的是基础语义能力，具体语法和更高层能力留有发挥空间。**

### 7.2 基础能力下限

总体要求是支持一般的、结构化的过程式计算：**顺序、选择、重复执行，以及用户定义函数与递归**。

| 类别 | 课件列出的基础要求 |
| --- | --- |
| 值类型 | 整数、字符串、布尔值、数组 |
| 运算 | 加、减、乘、除、模，比较，与、或、非 |
| 程序组织 | 变量、作用域、控制流、函数 |
| 配套能力 | 标准库等 |

这些要求是语言的下限。诸如整数宽度、除法语义、数组边界行为等细则，本讲没有给出，设计时需结合后续 Lab 规范明确。

### 7.3 可选拓展

课件表示，拓展内容**可能涵盖**原生并行编程支持、中端编译优化、高级类型系统。同学可以选择感兴趣的方向，建议结合拓展要求决定语言风格和设计。

这里保留课件的暂定语气，具体要求以后续发布为准。

### 7.4 测试、AI 使用与考核

Lab 借鉴 ECMAScript test262 测试集的思路，允许学生根据功能约束自行设计测试点，并鼓励测试驱动开发。

评价包括：

1. **自动评测：** 自行设计的测试点，加上隐藏输入的算法功能测试。
2. **学期末答辩：** 解释语言和编译器的设计与实现细节。

课程鼓励使用 AI 提高编码效率，同时要求保持独立思考，避免把设计和实现全盘交给模型。每个功能和语法都应有明确的设计目标与意图。

**补充理解：** 测试既用于发现实现错误，也帮助明确语言规则。例如，设计作用域时，应能用测试区分“内层同名变量遮蔽外层变量”和“修改外层变量”这两种行为。

## 9. 复习自测

1. **编译器转换程序时最重要的约束是什么？**  
   保持源程序的语义；对于不合法的源程序，还要给出诊断。

2. **为什么不从源代码文本直接完成所有优化？**  
   文本没有直接表达分析需要的全部关系。AST 突出嵌套结构，CFG 突出控制流，SSA 突出定义与使用，合适的表示能让相应算法更自然。

3. **语法分析通过后，为什么仍需要语义分析？**  
   结构符合文法，不代表名字能正确解析、类型能匹配；这些需要进一步检查。

4. **中端优化为什么需要程序分析？**  
   变换需要依据，例如某个值是否恒定、某个结果是否影响程序行为。分析为语义保持的变换提供事实。

5. **寄存器分配解决什么矛盾？**  
   程序中可能有大量临时值，机器的物理寄存器数量却有限；分配不下的值可能需要 spill 到内存。

6. **编译器与运行时如何分工？**  
   编译器处理静态可知的信息并生成代码，运行时处理依赖实际执行状态的工作，两者通过布局和调用等约定协作。

7. **新版 Lab 为什么强调自己设计测试并参加答辩？**  
   为了要求学生明确语言规则、验证语义能力，并能解释设计与实现，避免仅凭 AI 生成的代码形成“已经掌握项目”的错觉。
